O Dashboard é a maior superfície do produto e a única sem nenhuma cobertura automatizada.

São onze módulos, oitenta endpoints sob /dashboard/** e um front concentrado em apps/dashboard/app/dashboard-console.tsx — 2.950 linhas só no arquivo raiz, mais ~23.400 linhas somando todos os painéis de app/. O package.json do app traz apenas o placeholder "test": "node --test", e nenhuma das sete specs de apps/api/test/ toca uma rota de tenant: elas cobrem admin/*, RLS e autenticação.

Ao mesmo tempo, a branch atual acabou de extrair quatro painéis de dentro do console (home, privacy, branding, shop) e reestilizá-los com a biblioteca — a maior movimentação de código do dashboard em toda a história do repositório, feita sem rede de proteção. Este documento parte daí: prioriza o que está quente, ancora cada caso em uma regra literal da documentação do módulo e diz explicitamente o que não dá para testar hoje.

Convenções

  • Prioridade. P0 bloqueia o release — regra de negócio, dinheiro, permissão ou isolamento de tenant. P1 degrada a operação sem impedi-la. P2 é polimento e conveniência.
  • Camada. Cada caso carrega a etiqueta da camada em que deve ser implementado. UNIT é teste de método — função pura, sem banco e sem HTTP, escrito junto do código que ele prova. API é teste funcional no endpoint, com banco real e token de verdade. E2E é o que será automatizado pela interface, atravessando Dashboard, API e app do cliente. A etiqueta não é sugestão: um caso etiquetado UNIT que só existe como teste de API custa segundos a mais por execução e não aponta a linha que quebrou.
  • IDs. UNIT-<MOD>-nn para teste de método, API-<MOD>-nn para contrato de API e E2E-<MOD>-nn para jornada de ponta a ponta. A coluna Relação das tabelas unitárias aponta o caso de API que aquele teste de método sustenta — os dois não se substituem: o unitário prova a aritmética, o de API prova que ela chegou na resposta. A coluna Doc rastreia o ID de QA que já existe na especificação do módulo (AG-15, F-14, C-11…), para que este documento não crie uma numeração paralela.
  • Rastreabilidade. Todo caso P0 nasce de uma regra escrita em docs/dash/. Quando o caso é novo — descoberto pela heurística e não previsto na doc — ele aparece marcado novo.
  • Rota. O caminho literal do contrato OpenAPI, com os path params entre chaves: POST /dashboard/appointments/{id}/reschedule. Nunca abreviado com .../ nem com :id — é por esta string que a automação casa o caso com o endpoint, e abreviar quebra o casamento. Quando o caso precisa de arranjo, as rotas de preparação aparecem em cinza abaixo da rota sob teste: só a de cima é o alvo da asserção. Todas foram conferidas contra o docs-json; nos casos API-AN-01 e -02 a conferência é invertida, porque o ponto deles é a rota não existir.
  • Token. Qual login usar no before, lido do security da própria rota: tenantAuth é o administrador da organização, endUserAuth é o usuário final do app, platformAuth é o Super Admin e aberta é rota sem autenticação. Onde a mesma regra vale diferente para os dois perfis — o prazo de cancelamento em API-AG-19 e -20, por exemplo — os casos estão separados, um por audiência.
  • Status. O código HTTP esperado, para ir direto em paramsDefault.statusCode sem inferir do texto. 201 / 409 significa que o caso dispara duas requisições e espera um de cada. Todo código listado foi conferido contra os que a rota declara no contrato.
  • Asserção. A mensagem ou o campo que prova o caso — "Horário indisponível.", occupied == capacity, rescheduled_from_id != null. Onde antes se lia "400 com o campo inválido identificado", agora está escrito qual campo e qual mensagem.

1.1 O que já dá para reaproveitar

  • apps/api/test/admin-contract.integration.spec.ts — o padrão de teste de contrato a copiar: guarda de ambiente describeIntegration, bootstrap com Test.createTestingModule({ imports: [AppModule] }) e semeadura por pg.Pool de superusuário com slugs únicos por rodada (it-${Date.now().toString(36)}).

Três audiências de JWT convivem na API, todas HS256 assinadas com JWT_ACCESS_SECRET, TTL de 15 minutos e sem endpoint de refresh. Os guards leem apenas Authorization: Bearer <token> — não existe header de tenant; o tenantId viaja dentro do token.

1.3 Pré-requisitos que ainda não existem

Sem estes cinco itens, boa parte desta estratégia é intestável

  • Playwright instalado e configurado. Não há playwright.config.* no repositório. O único vestígio é a dependência em packages/ui, usada apenas por scripts/audit-rendered.mjs para capturas de tela.
  • Suíte de specs de tenant em apps/api/test/. Sugestão de organização: um arquivo por módulo (dashboard-appointments.integration.spec.ts, dashboard-forms.integration.spec.ts…), todos sobre o mesmo helper de seed.
  • Fábrica de tenant de teste com dois papéis distintos. Um Administrador Principal (is_primary_admin = true) e um administrador comum sem can_view_sensitive_data. Sem esse par, nenhum cenário de LGPD é executável — e LGPD é o eixo de permissão mais transversal do produto.
  • Controle do relógio. Janelas de 24 h e 7 dias na Home, limite de cancelamento de 24 h em Agendamentos e retenção em dias no LGPD dependem de tempo. Sem fake timers no backend ou semeadura com datas relativas, esses casos viram testes instáveis.
  • Extração da lógica pura para funções testáveis. Hoje quase nada do que esta estratégia etiqueta como UNIT é chamável isoladamente: a aritmética de janelas vive dentro de private async slots(db, …) (appointments.service.ts:72), a distribuição de grupos dentro de create(tenantId, actor, input) (groups.service.ts:156) e as janelas da Home dentro de home(tenantId, actorUserId) (dashboard.service.ts:43) — todas atrás de uma transação. Sem extrair essas funções para módulos sem db, todo caso unitário desta estratégia vira caso de API, que é exatamente o desequilíbrio que se quer corrigir.
  • Ambiente com add-on appointment_analytics ligado e desligado. GET /dashboard/appointments/analytics responde 400 quando o tenant não tem direito — precisa das duas configurações para testar os dois lados.

Restrição estrutural do front que muda o desenho dos testes E2E

apps/dashboard tem uma única rota, /. A navegação entre módulos é estado React (dashboard-console.tsx:357), não roteamento. Consequências diretas:

  • Deep link não existe. Toda jornada E2E precisa partir do login e navegar por cliques — não há como abrir /clientes direto.
  • Recarregar a página volta para a Home e descarta a subvisão. Isso é comportamento especificado (Menu, critério 8), não defeito — e por isso vira caso de teste.
  • Atalho legítimo: semear sessionStorage com crosshub.tenantToken e crosshub.tenantSlug para pular o login nos cenários que não estão testando o login. Vale lembrar do TTL de 15 minutos.

2. Análise transversal

Seis eixos que atravessam todos os módulos. Cada um gera um caso repetido em cada bloco — é o custo fixo da cobertura, e ignorá-lo é o jeito mais fácil de deixar um furo de segurança passar.

Cruzamento das dimensões

Agendamentos pontua em quatro das seis dimensões — Recent, Risky, Configuration-sensitive e Complex — e por isso abre este documento. É onde uma falha custa mais caro: um horário vendido duas vezes é um cliente na porta sem atendimento.

Mas o risco imediato, o que decide se esta branch pode ser mesclada, é outro: a regressão dos quatro painéis extraídos do console (Recent × Core). Extrair quatro painéis de um console de milhares de linhas sem nenhum teste é a operação mais perigosa em curso, e ela não tem nada a ver com regra de negócio — é fiação de props e token de cor. Daí o caso E2E-REG-01 ser tratado como pré-condição de merge, não como item de backlog.

12. Cobertura do contrato

Com a rota literal em cada caso, dá para cruzar a estratégia com o docs-json e medir o que ficou de fora. O número abaixo sai do próprio documento — não é estimativa.

88 dos 137 endpoints têm ao menos um caso

69 aparecem como rota sob teste; os demais entram como arranjo de outro caso. Nenhuma rota citada diverge do contrato. Dos 49 sem caso:

  • 13 são /admin/* — escopo do documento de estratégia do Admin, não deste.
  • 3 são /assets/* — entrega de binário, coberta indiretamente pelos casos de upload que conferem a publicUrl.
  • 33 são do Dashboard e ainda não têm caso. A maioria é leitura simples (GET de listagem, GET /dashboard/appointments/settings) exercitada de raspão como arranjo. As lacunas que merecem caso próprio: POST /dashboard/appointments/{id}/payments e .../refunds (dinheiro, sem caso dedicado além do extrato em API-AG-31), PATCH /dashboard/appointments/{id}/financial (desconto, acréscimo e isenção), PATCH /dashboard/appointments/{id}/edit (edição de agendamento, distinta da remarcação) e PATCH /auth/platform/public/me/profile (troca de e-mail exige senha atual).

Reproduzir a conta: node apps/api/scripts/generate-openapi.mjs /tmp/openapi.json e depois node docs/test-strategy/02/build-strategy-json.mjs /tmp/openapi.json, que confere cada rota citada e falha se alguma divergir.

Saída em dados

Ao lado deste HTML fica estrategia-testes-dashboard.json, com os mesmos casos em forma de dados. O HTML continua sendo a fonte — é onde o caso é escrito e revisado; o JSON é artefato de build, regerado por build-strategy-json.mjs. Existe para o projeto de automação parar de raspar HTML: sem ele, ligar caso a endpoint depende de heurística de sufixo, que é onde os casos se perdiam.

Campos de cada caso

  • rotas[] — cada uma com papel: acao é o alvo da asserção, arranjo é preparação, inexistente marca o caso cujo ponto é a rota não existir (API-AN-01 e -02).
  • token — tenantAuth, endUserAuth, platformAuth, ou null em rota aberta.
  • status[] — na ordem das asserções. [409, 200] em API-AG-19 são as duas bordas do prazo.
  • literais[] — as mensagens entre aspas extraídas da asserção, prontas para o expect.
  • campos[] — os identificadores citados em <code> na asserção.
  • doc e novo — rastreabilidade para docs/dash/, ou a marca de caso descoberto pela heurística.

Três pontos que o pedido da automação levantou

  • Contagem do painel. Estava em 159 contra 150 nas tabelas. O painel agora mostra 166, que é o número que sai do JSON — e o JSON é gerado do próprio HTML, então os dois não voltam a divergir.
  • Módulo de auditoria sem endpoint. Correto: o contrato não expõe nenhuma rota de auditoria, e não é omissão do openapi.json. A tabela audit_logs é escrita pelos serviços de domínio e hoje só é lida direto no banco. Os casos que a verificam (API-C-15, API-F-21, API-LGPD-13) fazem a ação por HTTP e conferem o registro por SQL — a pasta audit/ da automação é o lugar desses asserts, não de um cliente HTTP.
  • Fonte de verdade em API-AG-22. O código é a fonte: o cliente não remarca, só cancela. A especificação é que está desatualizada. O caso assertar 404 congela o comportamento atual de propósito — se a remarcação pelo cliente virar requisito, o teste falha e obriga a revisão, que é o efeito desejado.

13. A pirâmide proposta

A distribuição reflete uma decisão consciente: o peso vai para a camada de API — mas não porque a base unitária seja dispensável, e sim porque hoje ela é inalcançável: a lógica pura está trancada dentro de métodos privados que recebem uma transação. Cada caso UNIT-* marcado com extrair é, na prática, um pedido de refatoração pequeno e localizado; enquanto ele não acontecer, aquele comportamento continua sendo provado — mais devagar e com menos precisão — pela camada de API. O Dashboard é uma página só, com toda a lógica de negócio no backend — testar pela interface o que a API decide sairia caro e frágil. O E2E fica reservado para o que só existe na integração: dois aplicativos, duas audiências de token, e o que a interface promete além do contrato.

15. Critérios de saída

Condições para considerar o Dashboard homologado. Não são metas de cobertura percentual — são afirmações verificáveis.

  1. E2E-REG-01 verde antes do merge da branch atual. Os quatro painéis extraídos renderizam com os tokens da biblioteca e sem propriedade quebrada. Este item é pré-condição, não critério final.
  2. A camada unitária existe e roda sozinha. Os 46 casos UNIT-* executam sem banco, sem rede e sem subir o Nest, em um comando separado do de integração. Uma suíte unitária que precisa de Postgres não é unitária — é integração com outro nome, e perde a única vantagem que justifica a camada.
  3. 100% dos casos P0 executados e verdes, nas três camadas. Um P0 vermelho é bloqueio; não há exceção negociada por prazo.
  4. Zero vazamento entre tenants. O caso API-<MOD>-XT de cada um dos onze módulos passou, incluindo a variante que ignora a interface e chama a rota direto.
  5. As mensagens literais conferidas caractere a caractere — as duas de LGPD e as três de Agendamentos. A conferência acontece na camada unitária, sobre a constante exportada (UNIT-LGPD-03, UNIT-CAT-01); a de API confere que a mensagem chegou no corpo da resposta. Aproximação não conta em nenhuma das duas.
  6. Concorrência provada de verdade. API-AG-16 executado com disparo simultâneo real, repetido ao menos 20 vezes, sem nenhuma dupla confirmação.
  7. Nenhum dado de exemplo em produção. API-H-10 e E2E-H-02 passaram em tenant vazio — a especificação da Home alerta explicitamente contra reaproveitar os mocks do protótipo.
  8. Os fluxos destrutivos testados nos dois sentidos. Retenção (API-LGPD-11) apaga o que deve e preserva o que deve; remover acesso (API-AN-03) não anonimiza.
  9. Os limites duros confirmados. Três banners ativos, quatro ações na Home, dez eventos no feed, cinquenta grupos, cem itens por página.
  10. Os casos de volume executados com número registrado. Não é aprovação ou reprovação — é a evidência que decide a prioridade da paginação.
  11. As três decisões da seção 13 respondidas e refletidas nos casos correspondentes.

O que não é critério de saída

Cobertura percentual de linhas. Uma suíte com 80% de cobertura que não prova isolamento de tenant vale menos que quinze casos que provam. Os critérios acima são afirmações sobre comportamento, e é assim que devem ser reportados.
